# Adee's Food — Database Schema Proposal

**Platform:** Supabase Postgres
**Status:** Logical schema for Phase 0 review; not a migration
**Companion documents:** `ADEES_SYSTEM_ARCHITECTURE.md`, `ROLE_PERMISSION_MATRIX.md`, and the domain workflow documents

## 1. Modeling conventions

- Primary keys are UUIDs generated by Postgres. Human references such as order and purchase-order numbers are separate, unique fields.
- Business tables include `organization_id`; location-owned tables also include `location_id`.
- Mutable aggregates include `version integer not null default 1`, `created_at`, `created_by`, `updated_at`, and `updated_by`.
- Archive catalog/configuration rows with `archived_at`; do not soft-delete ledgers and transactional history.
- Money is `bigint` minor units plus `currency_code char(3)`; initial currency is `GHS`.
- Inventory quantities and conversions use bounded `numeric`; units may convert only within the same dimension.
- Time is `timestamptz` UTC; operational summaries also store the location-derived `business_date`.
- Core relations are normalized. JSONB is limited to immutable snapshots, redacted audit detail, provider metadata, and non-queryable configuration.
- All exposed business tables have RLS enabled and forced. Cross-scope composite foreign keys prevent organization/location mismatches.
- Status columns use database enums or constrained lookup values. Transitions are performed only by named commands.

| Type | Values |
|---|---|
| `order_status` | `DRAFT`, `CONFIRMED`, `IN_PROGRESS`, `FULFILLED`, `COMPLETED`, `CANCELLED`, `VOIDED` |
| `kitchen_status` | `NOT_REQUIRED`, `NOT_SENT`, `QUEUED`, `PREPARING`, `PARTIALLY_READY`, `READY`, `CANCELLED` |
| `payment_status` | `UNPAID`, `PARTIALLY_PAID`, `PAID`, `PARTIALLY_REFUNDED`, `REFUNDED` |
| `fulfillment_status` | `NOT_STARTED`, `READY_FOR_HANDOFF`, `SERVED`, `COLLECTED`, `DISPATCHED`, `DELIVERED`, `CANCELLED` |
| `order_type` | `DINE_IN`, `TAKEAWAY`, `DELIVERY` |
| `ticket_status` | `QUEUED`, `PREPARING`, `READY`, `CANCELLED` |
| `table_status` | `AVAILABLE`, `RESERVED`, `OCCUPIED`, `NEEDS_CLEARING`, `OUT_OF_SERVICE` |
| `reservation_status` | `PENDING`, `CONFIRMED`, `SEATED`, `COMPLETED`, `NO_SHOW`, `CANCELLED` |

| `close_status` | `DRAFT`, `SUBMITTED`, `CLOSED`, `REOPENED`, `SUPERSEDED` |

The four order status dimensions are intentionally independent. A dine-in order can be `IN_PROGRESS`, `READY`, `PAID`, and `READY_FOR_HANDOFF` at the same time.

### 3.5 Orders, pricing, settlement and fulfillment

| Table | Important columns and relationships | Constraints / purpose |
|---|---|---|
| `orders` | scope, order number, type, customer/table session, four statuses, business date, currency, subtotal/tax/charge/discount/total/due minor, version | Unique number per location; totals recomputed in DB |
| `order_items` | order, line number, item/variant references, name/SKU/price/tax snapshots, quantity, notes, four relevant statuses, recipe version, totals | Quantity > 0; completed line snapshots immutable |
| `order_item_modifiers` | order item, modifier reference, name/price snapshot, quantity | Unique line position; price snapshot immutable |
| `order_status_events` | order, dimension, from/to state, actor, reason, timestamp, version | Append-only transition evidence |
| `discounts` | scope, code/name, type/value, effective range, permission/limit, active | Constraints prevent negative totals |
| `order_discounts` | order/item, discount, calculated amount, reason, approver | Manual discount requires reason and permission |
| `payments` | order/customer, method, amount/currency, status, provider/reference, received by/at, idempotency key | Positive amount; unique provider reference where present |
| `payment_allocations` | payment, order, amount | Allocations sum cannot exceed successful payment |
| `refunds` | payment/order, amount, reason, status, requested/approved/processed data, provider reference | Cannot exceed refundable settled amount |
| `refund_lines` | refund, order item nullable, amount, quantity, reason | Supports itemized and goodwill refunds |

`CANCELLED` means an unfulfilled order was stopped before settlement/final completion. `VOIDED` is a controlled invalidation of a posted but not finally settled commercial document. A `REFUND` reverses money after a successful payment; it never rewrites the original payment.

## 4. Required database commands

The first implementation should expose a small, reviewed command surface rather than generic update access:

| Command | Atomic responsibilities |
|---|---|
| `create_order` / `update_order_draft` | Scope, price snapshots, modifiers, totals, version |
| `submit_order` | Validate sellability, confirm totals, allocate number, write events |
| `send_order_to_kitchen` | Route items, create tickets, set queue status, emit outbox event |
| `start_kitchen_ticket` | Lock ticket, set timestamps/status, post eligible recipe consumption once |
| `mark_kitchen_ticket_ready` | Update item/ticket/order kitchen rollup and notify service |
| `cancel_or_void_order` | Enforce state, approval/reason, item disposition, reversals/wastage, audit |
| `record_payment` | Recalculate balance, enforce method/reference, prevent overpayment policy breach |
| `record_refund` | Enforce refundable balance, approval, provider state, linked reversal |
| `complete_order` | Require allowed fulfillment/payment state, close table/order |
| `post_stock_count` | Freeze expectation, calculate variance, approve, create movements |
| `record_wastage` | Convert units, value loss, create movement and alert if threshold exceeded |
| `approve_purchase_request` | Check threshold/segregation, record decision |
| `issue_purchase_order` | Generate number, freeze commercial terms, record approval |
| `post_goods_receipt` | Validate PO/tolerance, create lots and stock movements once |
| `post_supplier_invoice` | Validate duplicates and match state, create financial event |
| `record_supplier_payment` | Allocate liability settlement and create financial/cash event |
| `submit_daily_close` / `post_daily_close` | Derive expected totals, record declarations, block unresolved exceptions, lock date |
| `reopen_daily_close` | Require owner/MFA/reason, preserve old close, unlock controlled corrections |

Exact SQL signatures belong in the implementation migration design after Phase 0 approval.

## 5. Cross-table invariants

1. An order's `paid_minor` equals successful payment allocations minus successful refund allocations; `due_minor` is derived and cannot be typed by a client.
2. An order may complete only when its required settlement and fulfillment rules pass. Exceptions require a named policy and audit event.
3. A kitchen-prepared order item routes to at least one active station before confirmation.
4. An order item consumes its pinned recipe version at most once unless a linked reversal exists.
5. `stock_balances` equals the sum of posted `stock_movements` for the same item/storage location/lot. A reconciliation job detects projection drift.
6. Posted stock, money and audit entries cannot be updated or deleted by application users.
7. Accepted goods receipt quantity is the only purchasing event that increases on-hand stock; a PO or invoice alone does not.
8. Supplier invoice posting creates a liability; supplier payment reduces it. Neither changes received quantity.
9. A posted daily close is computed from underlying transactions and exceptions; it is not a manually typed revenue record.
10. Records from different organizations or incompatible locations cannot be linked, even by an elevated UI.
11. All sensitive commands require a reason, current permission, and any configured approval/MFA at execution time.
12. Reversals reference the original entry and use the original currency/unit/cost basis unless a documented adjustment rule applies.

## 6. Index and partition strategy

Create indexes from measured query and RLS paths, including:

- every foreign key used in RLS or joins;
- `(organization_id, location_id, business_date)` on orders, payments, movements and financial events;
- partial indexes for open orders, active tickets, open table sessions, active reservations and unpaid invoices;
- unique partial indexes for one active role assignment, one open register/table session, one preferred supplier, one consumption posting, and external references;
- normalized phone/email indexes only where customer lookup is authorized;
- GIN only for demonstrated JSONB/search requirements.

High-volume immutable tables (`audit_events`, `stock_movements`, `order_status_events`, `financial_events`) may be time-partitioned after load measurement. Do not partition speculatively before queries and retention are known.

## 7. Migration, seed and test policy

- Migrations are forward-only, reviewed and applied automatically to staging before production.
- Generated Supabase TypeScript types are refreshed after each schema migration and checked in.
- Seed data includes permission codes, primary roles, units and deterministic test fixtures—not production personal data.
- Every table receives role/scope RLS tests for allowed and denied `SELECT`, `INSERT`, `UPDATE`, and `DELETE` paths.
- Command tests cover happy path, forbidden role, wrong location, invalid state, retry, concurrent execution, reversal, and ledger balance.
- Schema tests verify money/quantity constraints, cross-scope foreign keys, archive rules and immutable triggers.
- Restore and migration rollback procedures are rehearsed on staging before material production changes.
